# Voila (여행 블로그) 개발 로드맵

> 이 문서는 `docs/PRD.md`를 바탕으로 "어떤 순서로 만들지"를 정리한 개발 계획서입니다.
> 개발 초보자도 따라올 수 있도록 쉬운 말로 적었습니다.

## 한눈에 보기

| 단계 | 이름 | 예상 소요 시간 | 핵심 결과물 |
| --- | --- | --- | --- |
| 1 | 프로젝트 초기 설정 (골격) | 1~2일 | Next.js 15 프로젝트 + Notion 연결 준비 |
| 2 | 공통 모듈/컴포넌트 | 2~3일 | Notion 데이터 가져오는 함수 + 공통 화면 부품 |
| 3 | 핵심 기능 (MVP) | 3~4일 | 글 목록 / 글 상세 페이지 |
| 4 | 추가 기능 | 3~4일 | 여행지별 필터링 + 검색 |
| 5 | 최적화 및 배포 | 2~3일 | Vercel에 공개된 블로그 |

**총 예상 기간: 약 2~3주** (하루 2~3시간씩 작업한다고 가정한 대략적인 값이에요. 막히면 더 걸려도 괜찮아요!)

## 왜 이런 순서일까요?

집을 지을 때를 떠올려 보세요.

1. **골격(기초공사)**: 땅을 다지고 기둥을 세웁니다.
2. **공통(배관·전기)**: 모든 방에서 쓰는 물, 전기를 먼저 깝니다.
3. **개별 기능(방 꾸미기)**: 그 위에 거실, 침실을 하나씩 만듭니다.

기초 없이 방부터 꾸미면 나중에 전부 뜯어고쳐야 해요. 코드도 똑같아서, **골격 → 공통 → 개별 기능** 순서로 가야 다시 만드는 일이 줄어듭니다.

## 1단계: 프로젝트 초기 설정 (골격 구축)

**예상 소요 시간**: 1~2일

### 할 일
- [ ] 현재 Vite + React 프로젝트를 **Next.js 15 (App Router)** 로 전환하기
  - 현재 폴더는 Vite 스타터 킷이라 `vite.config.ts`, `index.html`, `react-router-dom` 등을 정리해야 합니다.
- [ ] TypeScript, Tailwind CSS 설정 확인하기
- [ ] 필요한 패키지 설치하기
  - `@notionhq/client` (Notion 연결)
  - `lucide-react` (아이콘)
  - shadcn/ui 초기 설정
- [ ] Notion에서 **데이터베이스 만들기** (PRD 5장의 속성 구조대로)
  - Title, Country, City, Tags, TravelDate, Cover, Status, Content
  - 테스트용 글 2~3개 작성 (`Status`를 `발행됨`으로)
- [ ] Notion **API 키(통합 토큰)** 발급하고 데이터베이스에 연결(공유)하기
- [ ] `.env.local` 파일에 API 키와 데이터베이스 ID 저장하기
  - `.env.example`에는 이름만 적어두기 (값은 비워두기)
  - `.env.local`이 `.gitignore`에 들어있는지 꼭 확인!
- [ ] 폴더 구조 정하기 (예: `src/app`, `src/components`, `src/lib`, `src/types`)

### 왜 먼저 해야 할까요?
모든 작업의 바탕이 되는 단계예요. 프레임워크(Next.js)와 Notion 연결이 준비되지 않으면 그 뒤에 만드는 어떤 기능도 확인해 볼 수 없습니다.

### 완료 기준
- [ ] `npm run dev` 실행 시 Next.js 기본 화면이 브라우저에 보인다.
- [ ] `npm run build`, `npm run lint`가 에러 없이 끝난다.
- [ ] Notion API 키로 데이터베이스를 한 번 불러보는 테스트가 성공한다.
- [ ] `.env.local`이 GitHub에 올라가지 않는 것을 확인했다.

## 2단계: 공통 모듈/컴포넌트 개발

**예상 소요 시간**: 2~3일

### 할 일
- [ ] **타입 정의**: 글(Post) 데이터의 모양을 TypeScript로 정리하기
  - 예: `id`, `title`, `country`, `city`, `tags`, `travelDate`, `coverUrl`
- [ ] **Notion 클라이언트 만들기**: API 연결을 한 곳에서 관리하는 파일 (`src/lib/notion.ts`)
- [ ] **데이터 가져오기 함수** 만들기
  - 발행된 글 목록 가져오기 (`Status`가 `발행됨`인 글만)
  - 글 하나의 본문 가져오기
  - Notion 데이터를 우리 타입(Post)으로 바꿔주는 변환 함수
- [ ] **공통 레이아웃**: 헤더(로고, 메뉴), 푸터, 전체 페이지 틀
- [ ] **공통 UI 부품** (shadcn/ui 활용): 버튼, 카드, 뱃지(태그 표시) 등
- [ ] **글 카드 컴포넌트**: 대표 사진, 제목, 여행지, 날짜를 보여주는 카드
- [ ] 로딩 중 / 에러 / 글이 없을 때 보여줄 공통 화면

### 왜 이 순서일까요?
글 목록 페이지와 상세 페이지는 **같은 데이터 함수와 같은 부품**(카드, 헤더, 태그)을 함께 씁니다. 공통 부분을 먼저 만들어 두면 같은 코드를 여러 번 쓰지 않아도 되고, 나중에 디자인을 바꿀 때도 한 곳만 고치면 돼요.

### 완료 기준
- [ ] 데이터 가져오기 함수를 실행하면 Notion의 글 목록이 터미널에 출력된다.
- [ ] `초안` 상태의 글은 목록에 나오지 않는다.
- [ ] 헤더와 푸터가 모든 페이지에 똑같이 보인다.
- [ ] 글 카드 컴포넌트가 가짜(임시) 데이터로 올바르게 보인다.

## 3단계: 핵심 기능 개발 (MVP)

**예상 소요 시간**: 3~4일

> MVP란 "꼭 필요한 기능만 먼저 만든 첫 버전"이에요. 이 단계가 끝나면 블로그로서 최소한의 모습이 갖춰집니다.

### 할 일
- [ ] **홈 페이지(글 목록)** 만들기
  - 발행된 글을 최신 여행 날짜순으로 카드 형태로 보여주기
- [ ] **글 상세 페이지** 만들기 (`/posts/[id]` 같은 주소)
  - 제목, 여행지, 날짜, 태그, 대표 사진 보여주기
  - Notion 본문(문단, 제목, 이미지, 목록 등)을 화면에 표시하기
  - 없는 글 주소로 들어오면 "찾을 수 없음" 페이지 보여주기
- [ ] 목록 카드를 클릭하면 상세 페이지로 이동하게 연결하기
- [ ] 기본 **반응형 레이아웃** 적용하기
  - 모바일 1열 → 태블릿 2열 → PC 3열
- [ ] 이미지 표시 설정하기 (`next/image`)
  - 참고: Notion 이미지 주소는 일정 시간이 지나면 만료되므로 이 점을 확인해야 합니다.

### 왜 이 순서일까요?
공통 부품이 준비되어 있으니, 이제 **블로그의 가장 중요한 두 화면**(목록, 상세)을 빠르게 조립할 수 있어요. 검색이나 필터 같은 부가 기능은 이 두 화면이 있어야 붙일 수 있기 때문에 뒤로 미룹니다.

### 완료 기준
- [ ] Notion에 새 글을 쓰고 `발행됨`으로 바꾸면 홈에 나타난다.
- [ ] 글을 클릭하면 본문 전체가 상세 페이지에 보인다.
- [ ] 휴대폰 화면과 PC 화면 모두에서 깨지지 않고 보인다.
- [ ] 존재하지 않는 글 주소에서 에러 대신 안내 페이지가 나온다.

## 4단계: 추가 기능 개발

**예상 소요 시간**: 3~4일

### 할 일
- [ ] **여행지별 필터링**
  - 국가/도시를 선택하면 해당 글만 모아 보여주기
  - 여행지별 목록 화면 만들기 (예: `/destinations/일본`)
  - 필터 선택 UI (버튼 또는 드롭다운)
- [ ] **검색 기능**
  - 제목 또는 키워드로 글 찾기
  - 검색 결과가 없을 때 안내 문구 보여주기
- [ ] **태그 클릭 시 같은 태그 글 모아보기** (여유가 있을 때)
- [ ] 필터/검색 상태를 주소(URL)에 반영하기 (예: `?country=일본`)
  - 새로고침하거나 링크를 공유해도 같은 결과가 보이게 됩니다.

### 왜 이 순서일까요?
PRD에서도 필터링과 검색은 **"MVP 이후에 추가"** 로 정했어요. 기본 목록·상세가 안정적으로 동작한 뒤에 얹어야, 문제가 생겼을 때 원인이 기본 기능인지 추가 기능인지 구분하기 쉽습니다.

### 완료 기준
- [ ] 국가/도시를 고르면 해당 여행지의 글만 보인다.
- [ ] 검색어를 입력하면 제목에 해당 단어가 있는 글만 보인다.
- [ ] 필터/검색 결과 화면도 모바일에서 잘 보인다.
- [ ] 결과가 없을 때 빈 화면 대신 안내 문구가 나온다.

## 5단계: 최적화 및 배포

**예상 소요 시간**: 2~3일

### 할 일
- [ ] **디자인 다듬기**: 색상, 글꼴, 간격, 다크 모드(선택) 등 정리
- [ ] **반응형 최종 점검**: 휴대폰 / 태블릿 / PC에서 모두 확인
- [ ] **속도 개선**
  - 이미지 크기 최적화
  - 데이터 캐싱 설정 (Notion을 매번 부르지 않고, 일정 시간마다 새로 불러오기 - ISR)
  - Lighthouse로 성능 점검
- [ ] **기본 SEO 설정**: 페이지 제목, 설명, 공유용 미리보기(OG 이미지)
- [ ] **에러 처리 점검**: Notion 연결이 실패해도 사이트가 깨지지 않게 하기
- [ ] **Vercel 배포**
  - GitHub 저장소 연결
  - Vercel 설정 화면에 환경 변수(API 키, DB ID) 등록
  - 배포된 주소에서 최종 확인
- [ ] 코드 정리 및 `README.md`에 사용법 정리

### 왜 마지막에 할까요?
기능이 다 만들어진 뒤에야 "어디가 느린지", "어디가 어색한지"를 정확히 알 수 있어요. 중간에 미리 최적화하면 기능이 바뀔 때 다시 해야 하는 경우가 많습니다. 배포는 모든 것이 준비된 마지막에 합니다.

### 완료 기준
- [ ] Vercel 주소로 접속하면 블로그가 정상적으로 보인다.
- [ ] Notion에서 글을 수정하면 잠시 후 배포된 블로그에도 반영된다.
- [ ] Lighthouse 점수(성능, 접근성, SEO)가 대체로 90점 이상이다.
- [ ] API 키가 코드나 GitHub에 노출되지 않았다.

## 주의사항

- **API 키는 비밀번호와 같아요.** `.env.local`에만 저장하고 GitHub에 올리지 마세요.
- Notion에서 글을 고친 뒤 블로그에 반영되기까지 **약간의 시간**이 걸릴 수 있어요. (캐싱 때문)
- 각 단계가 끝날 때마다 **Git 커밋**을 남기면, 문제가 생겨도 이전 상태로 쉽게 돌아갈 수 있어요.
- 막히는 부분이 생기면 무리하지 말고 한 단계씩 확인하며 진행하세요.
